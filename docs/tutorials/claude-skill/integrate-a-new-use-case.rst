Integrating a New Use Case with the Claude Skill
================================================

This tutorial walks through a complete integration: taking a standalone PyTorch training script
and turning it into an itwinai plugin that trains distributed on HPC, logs to MLflow, tunes its
hyperparameters with Ray, and produces a scalability report.

The example is a **Fourier Neural Operator (FNO) surrogate for 2D Darcy flow** — learning the
map from a permeability field :math:`a(x)` to the pressure field :math:`u(x)` that solves

.. math::

   -\nabla \cdot (a \nabla u) = f, \qquad u = 0 \text{ on } \partial\Omega

Learning a fast surrogate for an expensive solver is a core digital-twin pattern, which makes it
a more representative example than an image classifier. The data is generated by a small
finite-difference solver included in the script, so there is nothing to download and the whole
tutorial is reproducible offline.

.. note::

   You can follow this tutorial by hand, without Claude Code. Every file shown here is one you
   could write yourself, and the itwinai documentation covers each piece. The skill only
   automates the sequence.

Prerequisites
-------------

- itwinai installed (:doc:`../../installation/user_installation`)
- The skill installed (:doc:`../../getting-started/claude-skill`)
- For the later phases, access to a SLURM cluster

The starting point
------------------

The script lives at ``tutorials/claude-skill/fno-darcy/train.py`` in the itwinai repository. It
is deliberately ordinary — one file, ``argparse``, a hand-written loop, ``print`` for progress,
and ``torch.save`` for checkpointing. This is what scientific training code usually looks like
before integration.

.. code-block:: bash

   cd tutorials/claude-skill/fno-darcy
   python train.py --epochs 20

.. code-block:: text

   Generating training data...
   Data generated in 2.6s
   epoch 1/20  train 3.3577  val 1.6860
   epoch 2/20  train 0.8023  val 0.3856
   ...

Run this first. The baseline number matters: after porting, one epoch of the plugin must
reproduce it. That is the only way to know the move did not change the science.

Two features of this script determine everything that follows:

- The loss is a **relative L2 error**, the standard neural-operator metric. It is not one of the
  losses :class:`~itwinai.torch.config.TrainingConfiguration` knows about.
- The data is **generated**, not loaded, so the data step has to run a solver.

Starting the integration
------------------------

.. code-block:: text

   /itwinai:integrating-a-use-case

   > Integrate tutorials/claude-skill/fno-darcy/train.py into an itwinai plugin.

Phase 0 — Assess
----------------

The skill reads the script and records where everything lives, then makes one decision: whether
a custom trainer is needed.

.. list-table::
   :header-rows: 1
   :widths: 35 65

   * - Concern
     - Where it is now
   * - Model construction
     - ``FNO2d``, ``SpectralConv2d``
   * - Optimizer / scheduler
     - ``Adam`` + ``StepLR`` in ``main()``
   * - Loss
     - ``relative_l2`` — **custom**
   * - Training / validation loop
     - inline in ``main()``
   * - Dataset
     - ``make_dataset`` → ``TensorDataset``
   * - Hyperparameters
     - ``argparse``

**Decision: a custom trainer is required**, because ``relative_l2`` is not in
:class:`~itwinai.torch.config.TrainingConfiguration`'s allowed losses. Everything else is
conventional, so the trainer will be small.

.. tip::

   Most use cases go the other way. If the loss and optimizer are standard, no trainer subclass
   is needed at all — a ``DataGetter`` plus the stock
   :class:`~itwinai.torch.trainer.TorchTrainer` is enough. The MNIST plugin works this way.

Phase 1 — Scaffold
------------------

The plugin repository is created from
`itwinai-plugin-template <https://github.com/interTwin-eu/itwinai-plugin-template>`__ and the
package renamed to ``fno``:

.. code-block:: text

   fno-itwinai-plugin/
   ├── pyproject.toml
   ├── config.yaml
   └── src/itwinai/plugins/fno/
       ├── __init__.py
       ├── darcy.py      # the PDE solver and dataset generation
       ├── data.py       # the DataGetter component
       ├── losses.py     # relative L2
       ├── models.py     # FNO2d, SpectralConv2d
       └── trainer.py    # FNOTrainer

Every package directory must appear in the packaging configuration. Omitting one is the most
common packaging mistake, and it surfaces much later as an unrelated-looking ``ImportError``:

.. code-block:: toml

   [tool.setuptools.packages.find]
   where = ["src"]
   include = ["itwinai.plugins.fno"]

**Gate:**

.. code-block:: bash

   uv pip install -e .
   python -c "import itwinai.plugins.fno; print('ok')"

Phase 2 — Port
--------------

The script is split by concern. ``FNO2d`` and ``SpectralConv2d`` move to ``models.py``
unchanged — they are plain PyTorch and itwinai has no opinion about them. The solver and
``make_dataset`` move to ``darcy.py``, and ``relative_l2`` to ``losses.py``.

Data generation becomes a ``DataGetter``. Note the three mandatory pieces: the ``@monitor_exec``
decorator, the ``save_parameters`` call, and returning the full ``(train, validation, test)``
tuple:

.. code-block:: python

   from typing import Tuple

   import torch
   from torch.utils.data import Dataset, TensorDataset

   from itwinai.components import DataGetter, monitor_exec

   from .darcy import make_dataset


   class DarcyDataGetter(DataGetter):
       """Generate Darcy flow samples by solving the PDE on random permeability fields."""

       def __init__(
           self,
           n_train: int = 256,
           n_val: int = 64,
           grid_size: int = 32,
           seed: int = 0,
       ) -> None:
           super().__init__()
           self.save_parameters(**self.locals2params(locals()))
           self.n_train = n_train
           self.n_val = n_val
           self.grid_size = grid_size
           self.seed = seed

       @monitor_exec
       def execute(self) -> Tuple[Dataset, Dataset, None]:
           a_train, u_train = make_dataset(self.n_train, self.grid_size, self.seed)
           a_val, u_val = make_dataset(self.n_val, self.grid_size, self.seed + 1)

           mean, std = a_train.mean(), a_train.std()
           a_train, a_val = (a_train - mean) / std, (a_val - mean) / std

           return (
               TensorDataset(torch.from_numpy(a_train), torch.from_numpy(u_train)),
               TensorDataset(torch.from_numpy(a_val), torch.from_numpy(u_val)),
               None,
           )

``n_train`` is a constructor argument rather than a constant precisely so the dataset can be
shrunk from the config for the cheap verification runs later.

The trainer is the small part. It overrides one method, calls ``super()`` for all the standard
work — checkpoint loading, optimizer construction, distributing the model — and then substitutes
the loss:

.. code-block:: python

   from itwinai.torch.trainer import TorchTrainer

   from .losses import relative_l2


   class FNOTrainer(TorchTrainer):
       """FNO trainer. Identical to the stock trainer except for the relative L2 loss."""

       def create_model_loss_optimizer(self) -> None:
           super().create_model_loss_optimizer()
           # relative L2 is not among TrainingConfiguration's losses, so override it here,
           # after super() has built and distributed model, optimizer and scheduler.
           self.loss = relative_l2

That is the entire custom trainer. Resist the urge to override ``train_epoch`` as well: the
stock implementation already handles distribution, metric logging, profiling and checkpointing,
and reimplementing it silently discards all of them.

**Gate:** the plugin still imports, and no class shadows an itwinai name. ``FNOTrainer``, not
``TorchTrainer``.

Phase 3 — Wire
--------------

``config.yaml`` describes the pipeline. Hyperparameters go at the top and are interpolated, so a
single command-line override reaches every use of them.

.. code-block:: yaml

   run_name: fno-darcy
   strategy: ddp

   epochs: 20
   batch_size: 16
   lr: 1e-3
   grid_size: 32
   n_train: 256
   modes: 12
   width: 32

   training_pipeline:
     _target_: itwinai.pipeline.Pipeline
     steps:
       dataloading_step:
         _target_: itwinai.plugins.fno.data.DarcyDataGetter
         n_train: ${n_train}
         grid_size: ${grid_size}
       training_step:
         _target_: itwinai.plugins.fno.trainer.FNOTrainer
         epochs: ${epochs}
         run_name: ${run_name}
         strategy: ${strategy}
         model:
           _target_: itwinai.plugins.fno.models.FNO2d
           modes: ${modes}
           width: ${width}
         config:
           batch_size: ${batch_size}
           optimizer: adam
           optim_lr: ${lr}

**Gate — the first run that actually trains:**

.. code-block:: bash

   itwinai exec-pipeline --config-name config +pipe_key=training_pipeline \
     epochs=1 n_train=32

With no launcher and no Ray cluster, itwinai falls back to ``NonDistributedStrategy``, so this
runs on a laptop. Compare the loss against one epoch of the original script. If they disagree,
the port changed the science — fix that before continuing.

Phase 4 — Capabilities
----------------------

These are added **in order**. They form a dependency chain: the scalability report reads MLflow,
so the logger must exist before profiling, and both must be active during the scaling test.

**1. Logging**

.. code-block:: yaml

         logger:
           _target_: itwinai.loggers.LoggersCollection
           loggers:
             - _target_: itwinai.loggers.ConsoleLogger
               log_freq: 100
             - _target_: itwinai.loggers.MLFlowLogger
               experiment_name: FNO-Darcy
               run_name: ${run_name}
               log_freq: epoch
               log_on_workers: -1

``log_on_workers: -1`` matters. The default logs rank zero only, which is fine for losses but
leaves the scalability report without per-worker GPU data later.

.. code-block:: bash

   itwinai mlflow-ui --path mllogs/mlflow

**2. Distributed training**

No code changes. Add a ``slurm_config`` block to the same file and submit:

.. code-block:: yaml

   slurm_config:
     job_name: fno-darcy
     account: <your-account>
     partition: gpu
     time: "00:20:00"
     num_nodes: 1
     gpus_per_node: 2
     mode: single
     distributed_strategy: ${strategy}
     python_venv: .venv
     config_name: config
     config_path: .
     pipe_key: training_pipeline
     save_script: true
     pre_exec_file: <pre-exec script for your system>

.. code-block:: bash

   itwinai run -jc config.yaml

Remember that ``batch_size`` is **per worker**, so the effective batch size doubles on two GPUs.
A learning rate tuned on one GPU often needs adjusting.

**3. Profiling**

.. code-block:: yaml

         measure_epoch_time: true
         measure_gpu_data: true

**4. Hyperparameter optimization**

FNO has an unusually clean search space: the number of Fourier modes, the channel width, the
learning rate and the batch size.

.. code-block:: yaml

         ray_scaling_config:
           _target_: ray.train.ScalingConfig
           num_workers: 2
           use_gpu: true
         ray_tune_config:
           _target_: ray.tune.TuneConfig
           num_samples: 4
           scheduler:
             _target_: ray.tune.schedulers.ASHAScheduler
             metric: loss
             mode: min
             grace_period: 5
             reduction_factor: 4
         ray_run_config:
           _target_: ray.tune.RunConfig
           storage_path: ${itwinai.cwd:}/ray_checkpoints
           name: FNO-HPO
         ray_search_space:
           optim_lr:
             type: loguniform
             lower: 1e-5
             upper: 1e-2
           batch_size:
             type: choice
             categories: [8, 16, 32]

.. warning::

   Do not change ``strategy`` to a Ray value. itwinai detects a running Ray cluster and
   substitutes ``RayDDPStrategy`` automatically. Setting it by hand is the most common mistake
   when adding HPO. Set ``use_ray: true`` in ``slurm_config`` instead.

``storage_path`` must be absolute — hence ``${itwinai.cwd:}``.

Phase 5 — Scalability report
----------------------------

Optional, and it consumes real allocation.

.. code-block:: yaml

   slurm_config:
     mode: scaling-test
     scalability_nodes: "1, 2, 4, 8"

Submit, wait for **every** job to finish, then:

.. code-block:: bash

   itwinai generate-scalability-report

.. important::

   If the plots come out empty, the chain broke earlier. Check, in order: is ``MLFlowLogger``
   present, is ``log_on_workers: -1`` set, are the ``measure_*`` flags on, and did all jobs
   complete? The command exits successfully with no data, so there is no error to read.

See :doc:`../../how-it-works/scalability-report/scalability_report` for interpreting the output.

What to take away
-----------------

- **Most of the work is configuration, not code.** The only Python written here was a
  ``DataGetter`` and a three-line trainer override. Distributed training, logging, HPO and
  profiling were all config.
- **Override as little as possible.** The stock trainer does more than it appears to;
  reimplementing ``train_epoch`` would have silently removed checkpointing, profiling and
  distributed metric aggregation.
- **Verify at each step.** Import, then a one-epoch local run, then one node, then many. Each
  step has a small number of possible causes when it fails; skipping steps means debugging all
  of them at once.
- **The capability order is a real constraint**, not a stylistic preference.
