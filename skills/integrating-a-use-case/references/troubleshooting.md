# Troubleshooting

Work from the symptom. Do not advance past a failing gate by loosening the gate.

## `ModuleNotFoundError: itwinai.plugins.<name>`

In order of likelihood:

1. The subpackage is missing from `include` in `[tool.setuptools.packages.find]`. Every package
   directory must be listed, not just the top one.
2. A directory has no `__init__.py`.
3. The package was renamed but not reinstalled - `uv pip install -e .` again.
4. The wrong environment is active. `python -c "import itwinai; print(itwinai.__file__)"`.

The same cause produces a `_target_` resolution failure inside `exec-pipeline`, where it looks
like a config error. Check the import first, in isolation.

## Hydra cannot find the config

`--config-name` is the file name **without** `.yaml`. `--config-path` is its directory. Both are
relative to the launch directory, which under SLURM is not necessarily where the file lives -
this is why `slurm_config` has its own `config_path` and `config_name` fields.

## `pipe_key` is not recognised

It needs the `+` prefix: `+pipe_key=training_pipeline`. Without it Hydra tries to override a key
that does not exist in the config.

## Training runs on one GPU

Look for `Falling back to non-distributed strategy` in the job output. itwinai resolves the
strategy from the detected world size, so this is a launcher problem, not a config problem. Do
not change `strategy` in response. Confirm the SLURM script was generated by the builder, that
`num_nodes` and `gpus_per_node` are what you expect, and that the pre-exec file for the system
is being sourced.

## `Ray scaling config was passed, but it's ignored as Ray is not used`

No Ray cluster was detected. Set `use_ray: true` in `slurm_config` so the builder starts one.
This warning appearing once per `ray_*` block is normal for a non-HPO run.

## The scalability report is empty

Walk the chain in `references/profiling-and-scalability.md` from the left:

1. Is `MLFlowLogger` in the pipeline at all?
2. Is `log_on_workers: -1` set on it? The default logs only rank zero, so per-worker GPU data
   never arrives.
3. Are `measure_epoch_time` and `measure_gpu_data` both true?
4. Did **every** scaling-test job finish? A report generated while jobs are queued omits them
   silently and looks like a scaling cliff.
5. Do `--experiment-name` and `--run-names` match what was actually logged?

The command exits successfully with no data, so there is no error message to find.

## `ValueError` about `store_torch_profiling_traces`

It requires `enable_torch_profiling: true`. Set both or neither.

## Ray fails on `storage_path`

It must be absolute. Use `${itwinai.cwd:}/ray_checkpoints`.

## pydantic validation error on `slurm_config`

A key name does not match the schema. Read `MLSlurmBuilderConfig` in
`itwinai/slurm/configuration.py` - it is the source of truth. Note `distributed_strategy`, not
`dist_strat`, which appears in one published plugin and is stale.

## The generated SLURM command does not match what I configured

`{}` slots in `training_cmd` are filled by the builder from `slurm_config` fields. Overriding one
of those fields on the command line desynchronises the two. Change them in the file. Set
`save_script: true` and read the generated script.

## The ported code trains differently from the original

A porting bug, not a tuning problem. Same seed, same data, one epoch, both versions, compare the
loss. Common causes: the loss silently resolved to a `TrainingConfiguration` default instead of
the original one; a transform dropped during the move; the optimizer rebuilt with different
defaults; shuffling changed. Revert to the original and re-port in smaller steps.

Note that per-worker batch size means the effective batch size scales with GPU count, so a
distributed run legitimately differs from a single-GPU one. Compare non-distributed against
non-distributed first.

## Out of memory when scaling up

`batch_size` in `config:` is per worker, not global. It does not need reducing when adding GPUs -
if it OOMs at higher node counts, something else grew, typically dataloader workers or a cached
dataset held per process.

## MLflow works locally but not in the job

A `tracking_uri` that resolves on the login node may be unreachable from compute nodes. Leave it
`null` to use the filesystem backend under `mllogs/mlflow`, and inspect afterwards with
`itwinai mlflow-ui --path mllogs/mlflow`.

## Still stuck

`itwinai sanity-check --torch` verifies the installation itself.
`itwinai check-distributed-cluster` exercises the torch-distributed network setup and must be
run under `torchrun` or with a Ray cluster up. If neither shows a problem, reduce to the
smallest failing case - one node, one GPU, one epoch, truncated dataset - before investigating
further.
